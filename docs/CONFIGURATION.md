# Configuration code reference

Strict JSON files use this companion documentation rather than nonstandard JSON comments. TOML, environment examples, Docker/Compose, SQL, and TypeScript carry inline comments alongside their implementation.

## `package.json`

- `type: module` establishes the first-party ESM boundary.
- `packageManager` and `engines.bun` pin the development/production runtime.
- `build` runs `scripts/build.ts`, which removes stale generated modules, compiles TypeScript, and builds the isolated Nodestone worker.
- `typecheck` includes source, tooling, tests, and declaration contracts; `lint` enforces first-party ESM and the explicit-any rule.
- `format` and `format:check` use the shared Biome rules.
- `start` executes the compiled composition root.
- `test:unit`, `test:contract`, and `test:integration` separate pure/module behavior, external boundaries, and real PostgreSQL persistence. `test:docker` supplies a disposable complete environment.
- `commands:register` discovers command definitions and explicitly overwrites the selected development/production inventory. It confirms the token's application first and refuses `--global` while `TEST_GUILD_ID` is set.
- `commands:list` and `commands:clear-guild` run `scripts/commands.ts` over Discord REST only. `list` reads back the global scope and every guild scope and exits 2 unless the declared scope matches exactly and every other scope is empty. `clear-guild GUILD_ID --application APP_ID` prints a dry run with a fingerprint and clears that one guild scope only with `--confirm FINGERPRINT`; nothing clears the global scope.
- `app:spec` runs `scripts/app-spec.ts`, which derives the `foundation`, `maintenance`, and `full` App Platform phases from `.do/app.yaml` or an exported live spec ([APP_PLATFORM.md](APP_PLATFORM.md#deployment-phases)).
- `nodestone:check` compares the Nodestone submodule checkout and selector lockfile snapshot with their upstream HEADs. `nodestone:update` advances them, records exact revisions/source fingerprints, and checks the build/contracts; `--deploy` rebuilds and restarts the sidecar.
- `ci:version` validates the SemVer increment, changelog entry, and any release tag before publication. `test:fixture` generates invented migration input for public CI under `.cache/ci/legacy.sql`; `LEGACY_FIXTURE_PATH` selects it for integration or Docker tests.
- Migration/import/snapshot/acquisition/preview/activation/retry scripts execute compiled one-shot tooling. Their file headers explain their maintenance boundaries. For production and rehearsal, run the compiled files directly with `bun --env-file` rather than these `bun run` aliases (see [Maintenance-tool profiles](#maintenance-tool-profiles)).
- Runtime dependencies support active bot operations, including pinned `drizzle-orm` with the existing `pg` driver. Build-only Nodestone source/selectors and TypeScript tooling are development dependencies; the sidecar worker is compiled into its image.

`bun.lock` is generated by Bun and pins transitive packages and source revisions. Dependency changes are made through Bun and verified with frozen-lockfile installation.

`.do/app.yaml` is the production App Platform spec. Its shared release tag follows the manifest, its database component attaches the owner-provisioned Managed PostgreSQL cluster `tarubot-pg` (`production: true`, database and user `tarubot`), and the migration job uses the bot image. The worker-free phases used to create and maintain the app are derived from it with `app:spec`. `DATABASE_CA_CERT` accepts the provider PEM root CA and gives the shared database boundary verified TLS across the runtime and maintenance commands. See [APP_PLATFORM.md](APP_PLATFORM.md).

Nodestone uses the `vendor/nodestone` Git submodule through a local `file:` dependency; initialize it before installation/builds. Selectors retain a floating `#HEAD` manifest reference. The updater follows HEAD for both repositories. `sidecar/upstream-revisions.json` records tested commits and the parser-source fingerprint; the submodule pointer and selector lock preserve reproducible builds. The runtime periodically checks for newer upstream commits.

## `tsconfig.json`

`resolveJsonModule` includes the package manifest in compiled output. `/version` uses that build-local copy, so its reported SemVer identifies the deployed application. The source manifest and [CHANGELOG.md](../CHANGELOG.md) define the version policy and milestone numbering.

| Option | Reason |
| --- | --- |
| `target: ESNext` | Emit modern JavaScript supported by pinned Bun |
| `module`, `moduleResolution: NodeNext` | Native ESM semantics with explicit runtime-relative `.js` imports |
| `strict` | Require explicit null/error handling and safe inference |
| `noUncheckedIndexedAccess` | Array/map lookups can be absent |
| `exactOptionalPropertyTypes` | Omitted properties differ from explicitly undefined values |
| `noImplicitOverride` | Make subclass contract changes visible |
| `noFallthroughCasesInSwitch` | Prevent accidental dispatch fallthrough |
| `verbatimModuleSyntax` | Preserve ESM and require explicit type-only imports |
| `forceConsistentCasingInFileNames` | Keep imports portable across host/container filesystems |
| `skipLibCheck` | Leave separately packaged dependency declaration internals outside first-party checking |
| `types: [bun]` | Type Bun APIs and test facilities |
| `rootDir`, `outDir` | Preserve module directory layout under `dist/` |
| `sourceMap` | Keep production diagnostics traceable to TypeScript source |
| `include` | Check all first-party source, operational scripts, sidecar code, and tests |

`tsconfig.build.json` inherits those guarantees and emits application/tooling/sidecar code. Tests are independently type-checked and executed through Bun. Declaration-only files describe narrow dependency boundaries.

## `biome.json`

- File selection excludes dependencies, generated output, working caches, imported data, and the requirements contract.
- Formatting uses two-space indentation, double quotes, semicolons, and a 100-column target.
- `noCommonJs` and `noExplicitAny` enforce the first-party module/type contracts.
- Automated import/code assists are disabled so the formatter does not silently restructure source.

## Runtime configuration

`.env.example` comments identify credentials, scope, activation, timing, health, and resource budgets. Validation lives in `src/config/env.ts` and the Nodestone adapter/sidecar. Detailed runtime settings are in [OPERATIONS.md](OPERATIONS.md) and [NODESTONE.md](NODESTONE.md). `RESTORE_DATABASE_CA_CERT` optionally gives `check-restore`'s `RESTORE_DATABASE_URL` its own CA (a PITR fork is a new cluster); empty reuses `DATABASE_CA_CERT`.

`production.env.example` is the tracked template for the production maintenance-tool environment. It lists every `.env.example` key with production values, a direct-port (25060) managed-cluster URL placeholder, a quoted multi-line CA placeholder, and an empty token, so no development value can fill a gap. Copy it outside any checkout (for example `~/tarubot-cutover/production.env`, mode 600); never name the copy `.env` or `.env.production`. Git and Docker ignore `*.env` files; the two templates stay tracked.

## Maintenance-tool profiles

`src/config/deployment.ts` is a deployment-identity guard. Every maintenance tool that touches Discord or PostgreSQL calls it once, after parsing arguments and before any I/O: `migrate`, `register`, `commands`, `snapshot`, `import` (publishing only; dry runs use no credentials), `acquire`, `preview`, `activate`, `retry`, `check-restore`, `discord-inspect`, and `discord-smoke` (DevBot only). The bot runtime itself is unchanged; it checks only that its token belongs to `DISCORD_APPLICATION_ID`. Refusals are `configuration` failures that name settings, hosts, and database names, never a URL, password, or token.

**Profile selection.** `TARUBOT_ENVIRONMENT=production` or `rehearsal` selects that profile. `devbot`, or DevBot's application ID `943291473477128243` with the variable empty, selects DevBot. The production application ID `965294750741692416` without an explicit marker is refused. Anything else is `unmanaged` (CI and other developers).

| Profile | Application and scope | Databases |
| --- | --- | --- |
| `production` | `965294750741692416`; `TEST_GUILD_ID` and `TEST_PLAN_CHANNEL_ID` empty and `PUBLIC_TEST_RESPONSES` not true; guild `1036062273631952955` only; the only profile that may register the global command set, and it registers nowhere else (`register.js --guild` is refused) | Managed host only, with a CA, the direct port 25060, and user exactly `tarubot`; never `tarubot_dev`, `*_test`, or `*_rehearsal`. A restore target is `tarubot_restore` on the primary's host or `tarubot` on another host (a PITR fork). |
| `rehearsal` | As production, but read-only on Discord (registration and command cleanup are refused) | `DATABASE_URL` ends in `_rehearsal`, and a restore target in `_restore_test`. A managed host needs the CA, port 25060, and a user other than `doadmin`. |
| `devbot` | `943291473477128243` with `TEST_GUILD_ID=1040379370159743139`; that guild only; no global registration | Local host (loopback, the Compose `postgres` service, or Docker's host alias) with an empty CA; `DATABASE_URL` names exactly `tarubot_dev`, and a restore target ends in `_restore_test`. Only `migrate.js --restore-rehearsal` may name a `*_restore_test` copy as `DATABASE_URL`, to rehearse a migration there first ([OPERATIONS.md](OPERATIONS.md#restore-rehearsal-local-compose-and-devbot)). Production and rehearsal refuse that flag. |
| `unmanaged` | May not touch either managed deployment's guilds or use its token | No deployment-specific rules |

Every database URL must carry its host, port, user, and database itself; `host`, `hostaddr`, `port`, `user`, `dbname`, and `database` query parameters are refused, and a restore target must differ from `DATABASE_URL`. After authenticating, tools that use Discord confirm that the token belongs to the profile's application before reading any guild or command. `commands.js clear-guild` never touches the profile's own registration scope (DevBot's guild), and under production it clears only guilds the application belongs to.

**Owner action for DevBot.** The DevBot profile requires the local `.env` to point local tools at `…/tarubot_dev`. A `.env` whose `DATABASE_URL` names `…/tarubot` is refused until the owner changes it; the Compose overlay already gives the running bot `tarubot_dev`.

**Launch rule and verified Bun 1.4.2 behavior.** Production and rehearsal runs are refused when an auto-loaded env file (`.env`, `.env.local`, `.env.production[.local]`, `.env.development[.local]`, or `.env.test[.local]`) exists in the working directory and the process was started without `--env-file`. The reasons, each verified with Bun 1.4.2:

- `bun --env-file=FILE` loads only that file; the working directory's `.env` family is not loaded.
- A `bun run` script child reloads the working directory's `.env` for every key the parent did not set, even when the parent used `--env-file`, so development values fill any gap.
- With `NODE_ENV=production` and no `--env-file`, Bun also loads `.env.production`.
- Variables already in the environment, such as shell exports, override the file.

The production invocation is therefore `env -i HOME="$HOME" PATH="$PATH" bun --env-file=PATH dist/scripts/TOOL.js`, from a clean clone of the deployed release, never `bun run` ([MIGRATION.md](MIGRATION.md) E0). Containers have none of these files; the App Platform worker and migrate job set `TARUBOT_ENVIRONMENT=production`.

## Database schema

`migrations/001_initial.sql` documents each domain/table and the important database-enforced invariants. Once applied outside disposable development/rehearsal databases, migration contents—including comments—must remain immutable because startup and migration tooling validate checksums. Add subsequent changes as new numbered migrations and update the expected schema version.

`src/infrastructure/postgres/schema.ts` maps the applied schema for Drizzle queries and inferred record types. SQL migrations remain the deployment authority; there is no automatic schema synchronization or Drizzle Kit push step. The current 2.14.0 source adds no migration and requires `005_launch_access_policy.sql` (from 2.13.0), which adds `grandfathered` guest-grant provenance, the once-only first-activation grandfathering marker, and the per-guild role-layout switch (on by default, backfilled off for imported guilds). Channel onboarding still defaults off until `/setup`. See [PERSISTENCE.md](PERSISTENCE.md) for query, connection, and exact-value conventions.
